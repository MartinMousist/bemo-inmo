## Lo que se pidió y lo que se hizo

El pedido original fue: *seguir con todo lo de `CONTINUAR.md`, hacer una landing
como appmiti.com, sincronizar la API de Google, y pensar mejoras para el
roadmap*. Después, dos veces: **"hacé todo lo que falte"**.

### Bloque 1 — Lo que fallaba solo (prioridad 1 del documento)

**Límite de intentos en `/auth`.** No había ninguno. Dos contadores con nombre:
por IP (10 cada 15 min) y por cuenta (20, más alto **a propósito** — un tope
bajo por cuenta es un arma: cualquiera puede dejar afuera a un usuario real
quemándole los intentos). El 429 sale con el mismo contrato RFC 9457 que el
resto.

**Paginación** en `ventas`, `liquidaciones`, `publicaciones`, `avisos` e
`indices`. El plan Medio vende 500 propiedades: estas listas se rompían *dentro
del límite que se cobra*. `avisos` además tenía un `LIMIT 200` pelado, que no es
paginar sino truncar en silencio.

**Seis N+1 pasados a lote.** El peor, `liquidaciones.generar`, hacía ~6 consultas
por propietario más 2 por línea; ahora son 5 en total para todo el mes.

### Bloque 2 — Producto

- **Pantalla de inicio** (`/inicio`): qué hay que resolver hoy. Aumentos por
  confirmar, cuotas impagas con su mora, lo que vence en siete días,
  liquidaciones sin cerrar, consultas frías.
- **Cartera de alquileres**: una fila por contrato con próximo aumento, última
  cuota, saldo y estado de cobranza. Acciones en línea y selección múltiple.
- **Toasts y confirmación** para lo irreversible, con los montos a la vista.
- **Portada**: se agregó el bloque del problema, las garantías y el cierre.

### Bloque 3 — Google Maps

El circuito quedó completo: diagnóstico que le pega a Google de verdad, backfill
de las propiedades cargadas antes de tener la key, y panel en Propiedades.
Falta **sólo la key**.

### Bloque 4 — Etapa 10 (las mejoras que salieron de recorrer el código)

- **Punitorios por mora**, con motor puro y 14 casos de papel.
- **Renovación de contrato** y **devolución del depósito**.
- **Auditoría de la plata** + el estado `pagada` de las liquidaciones.
- **Segunda tanda de paginación** (`vencimientos`, `periodos`, `ajustes`).
- **Request-id y logging estructurado.**
- **Backup automático**, verificado restaurando.
- **45 tests de frontend** con Vitest, donde había cero.
- **Caja del día**, **auditoría en pantalla**, **⌘K completa**.
- **Portal del propietario**, **notas de seguimiento**, **recibo de cobro**.
- **Deploy**: compose de producción, Caddy, guía.
- **Contador de intentos compartido** en Postgres.
- **Accesibilidad**: contraste medido, teclado en tablas, 375px.

## Los bugs reales que aparecieron

Esto es lo más útil de este documento. Ninguno se encontró leyendo: todos
salieron de escribir un test o de mirar el navegador.

### 1. Bug de plata: rearmar una liquidación borraba los gastos

`liquidaciones.generar` borraba **todas** las líneas y después sumaba los gastos
desde la tabla que acababa de vaciar. `totalGastos` daba siempre 0.

Un termotanque de ARS 85.000 adelantado por la inmobiliaria se le transfería de
más al propietario en cuanto alguien regeneraba el período — y `generar` es
idempotente y se corre varias veces por mes. **Con test de regresión.**

### 2. `@SkipThrottle()` sin argumentos no salta contadores con nombre

Salta el contador llamado `default`; los nuestros se llaman `ip` y `cuenta`. El
decorador pelado no saltaba nada. Habría dejado `/auth/yo` limitado a 10 por
ventana — y el front lo llama en **cada carga de página**: una oficina detrás de
una IP se quedaba sin sesión a media mañana. Lo encontró el test de `logout`.

### 3. Un aumento confirmado y vigente se mostraba como "próximo aumento"

Ése es el alquiler de hoy, no algo por resolver. La columna decía `01/04`
mientras el aumento que faltaba confirmar (`01/07`) quedaba invisible.

### 4. `cerrar` no marcaba los cobros de punitorio (bug que casi introduzco)

Marcaba como liquidados sólo los cobros de las líneas de alquiler. El cobro de
un interés habría vuelto a entrar en la liquidación del mes siguiente. Y del
siguiente.

### 5. La portada prometía el dólar como índice

No existe entre los `INDICES`. Un índice inventado en la portada es el mismo
error que un precio inventado.

### 6. El compose nunca le pasaba `GOOGLE_MAPS_API_KEY` al contenedor

Con la key en el `.env`, la API seguía sin verla. Ése solo era el motivo de que
"el código está listo" no alcanzara.

### 7. El CI nunca había corrido, y al correr encontró un agujero

Se publicó el repo y el workflow arrancó solo por primera vez. **Falló**:
levantaba Postgres pero no S3, así que los diez tests de fotos no corrían.

No es un detalle de infraestructura. Entre esos tests está el que verifica que un
archivo se acepte por su **firma de bytes** y no por su nombre — el que impide
subir un ejecutable llamado `foto.jpg`. Un CI que no corre ese test da luz verde
a un cambio que rompe esa validación. Con MinIO agregado, en verde.

### 8. Los dumps de la base estaban versionados

Tres archivos con la base de desarrollo entera. Se sacaron del historial antes de
publicar el repo. Y `.gitignore` tenía una lista explícita de `.env` que **no**
cubría `.env.prod`.

## Trampas nuevas para `CONTINUAR.md`

Ya están agregadas ahí, pero conviene tenerlas juntas:

| Trampa | Causa |
|---|---|
| `unnest` y el orden del `RETURNING` | El orden de las filas que devuelve un `INSERT` no lo garantiza el motor. En `ventas`, el encadenado padre→hijo se mapea por `punta`, no por posición |
| Índices en los tests | Son **globales** y no se limpian entre corridas. Un test cargó `icp` "porque estaba vacío" y rompió otro. Cada suite usa su propio año y acota con `desde`+`hasta` |
| El índice del ajuste | El motor usa el índice del **mes anterior**: cargar sólo los meses del ajuste no proyecta nada |
| Comillas invertidas en un template literal | Un comentario SQL con `` `columna` `` adentro de un `` ` `` rompe el string |
| El watcher del contenedor se traba | Después de un error de compilación intermedio deja de recompilar. `docker compose restart api` |
| El seed usa UUIDs `1111…` | Elegir uno "obvio" para datos de prueba choca con el seed |
| El trigger de límite de plan usa `app_current_tenant()` | Sin contexto devuelve tope 0. Al cargar datos como owner hay que fijarlo a mano |
| Ya existía una tabla `auditoria` | De la migración 003. La migración nueva falló al aplicarse, y estuvo bien: dos registros de auditoría son peores que ninguno |

## Decisiones de dominio que se tomaron

Van acá porque **no son obvias** y alguien las va a querer discutir de nuevo:

1. **A quién le corresponde el punitorio lo decide el CONTRATO**
   (`punitorio_para`), no una regla global. En la mayoría compensa al
   propietario por la plata que no cobró a tiempo, pero es negociable. El
   default es `propietario`: es el que no le da plata extra a quien administra
   sin que el dueño lo haya acordado.

2. **Sobre el punitorio no se cobran honorarios.** Son un porcentaje del
   alquiler pactado, no de la mora. Cobrarlos sería cobrar dos veces por el
   mismo atraso.

3. **El interés es simple, no compuesto.** El contrato dice "X% diario" y eso,
   en la práctica argentina, es simple. Capitalizarlo daría un número que el
   inquilino no puede rehacer con una calculadora — y un punitorio que no se
   puede verificar no se cobra: se discute.

4. **Una cuota vencida a medio pagar es MORA, no "parcial".** Como parcial se
   pierde entre las que están en camino y nadie la reclama.

5. **Renovar deja el anterior en `renovado`, no en `vencido`.** Uno es una
   propiedad que se desocupó; el otro, el mismo inquilino que sigue.

6. **El portal del propietario NO es un usuario.** No tiene contraseña, no entra
   a la app y no puede escribir nada. Darle una membresía sería meterlo adentro
   del sistema para que mire una pantalla.

7. **El contador del rate limit va en Postgres, no en Redis.** La base ya está,
   ya es estado compartido y ya se respalda. Los intentos de login son decenas
   por minuto, no miles por segundo.

8. **Lo que queda sin paginar es una decisión escrita, no un olvido**:
   `equipo`, `plantillas` y `comisiones/por-agente` — este último es un
   agregado, y paginarlo sería partir un total en pedazos. Está en un test con
   su motivo.

## Medición con volumen real

`./scripts/medir-cartera.sh 500` carga 500 contratos, 12.000 cuotas y 9.000
cobros en un tenant descartable, mide y borra lo que cargó.

| Consulta | Tiempo |
|---|---|
| Cartera (página de 50) | 19,6 ms |
| Inicio · por cobrar del mes | 6,1 ms |
| Inicio · cuotas impagas | 7,2 ms |
| Vencimientos (90 días) | 1,3 ms |

**No hace falta optimizar nada** — que era la hipótesis del roadmap. Optimizar
sobre una hipótesis es el error #4 del playbook con otra cara.

## Lo que NO se pudo hacer

### appmiti.com no es alcanzable

Se intentó por navegador, por `WebFetch` y por `curl`. El dominio resuelve a una
IP de AWS (`18.204.152.241`) pero el servidor **nunca responde**: timeout de TCP.
Tampoco está indexado.

**La portada actual NO es una réplica de esa página**: es la arquitectura
estándar del género con marca y copy propios. Para replicar su estructura hacen
falta **capturas**.

### El deploy no está verificado

Los artefactos están escritos y probados hasta donde se puede sin servidor: las
dos imágenes compilan, el compose valida, el Caddyfile valida y el build produce
los assets con hash. **Un deploy real no se hizo** porque no hay dónde. El punto
del roadmap queda abierto.

## Lo que queda abierto, y de qué depende

Nada de esto es "escribir el código que falta".

| Qué | De qué depende |
|---|---|
| **El precio** | Que alguien diga un número. Es el gate de la etapa 0 y no lo destraba ningún código |
| **Expensas: quién las cobra** | Una decisión de negocio. Cambia el neto de la liquidación |
| **La API key de Google** | Crearla. Los tres pasos están en `.env.example`. **Ojo: restricción por IP, no por referrer HTTP** |
| **Capturas de appmiti** | Que el sitio responda, o que las saques vos |
| **Deploy, TLS, dominio** | Un servidor. La guía está en `docs/deploy.md` |
| ~~**Verificar CI**~~ | **Hecho.** Ver abajo |
| **Tres liquidaciones reales** | Las tuyas. Es el gate de la etapa 4 |
| **Medir con 5.000 contratos** | Sólo si la cartera crece diez veces |
| **Contraste en modo oscuro de los chips sobre fondos de color** | Medido y en verde; queda revisar los estados de foco dentro de las tablas |

### Una pregunta abierta que ya no lo está

*"¿Cómo se tratan los punitorios en la liquidación?"* era una de las cinco
preguntas del gate de la etapa 0. Ahora se calculan, se condonan con motivo, y a
quién le corresponden lo decide cada contrato.

**Falta que confirmes que el default —el interés va al propietario— es el que
usás vos**, o si lo retenés como compensación por la gestión de cobranza.

## Comandos útiles

```bash
docker compose up -d                        # db + s3 + api + web
docker compose exec api npm test            # 437 tests contra Postgres real
docker compose exec web npm test            # 45 tests de front
docker compose exec api npx tsc --noEmit
docker compose exec web npx vue-tsc --noEmit

./scripts/medir-cartera.sh 500              # mide con volumen real
./scripts/backup.sh                         # backup a mano, con verificación
docker compose --profile backup up -d       # backup automático y diario
```

**Trampa conocida**: las dependencias se instalan **dentro** del contenedor
(`docker compose exec api npm i <paquete>`). El `node_modules` vive en un volumen
anónimo; instalar sólo en el host no rompe al instalar, rompe al reiniciar.
